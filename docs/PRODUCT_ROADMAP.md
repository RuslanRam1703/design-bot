# Единый план Design Assistant — 2026-11-11

`DONE` — реализовано и проверено автоматически; `PARTIAL` — закрыта часть;
`MANUAL TEST PENDING` — нужен реальный Telegram/мобильный тест;
`BLOCKED` — требуется внешнее действие. CI не заменяет пользовательскую приёмку.

## Продукт и архитектура

Один существующий Telegram-бот, Mini App и административный интерфейс.
`leads.json` в Upstash связывает заявку, бриф, статусы, материалы, переписку,
проект и журнал доставок. Клиентская личность проверяется по Telegram initData;
административные действия ограничены владельцем. FSM использует тот же Upstash.
Приватный форум-архив — вторичная копия, публичный канал — источник портфолио.
Новые реестры, платные ресурсы, миграции и очистка production не требуются.

## Свойства доставки

- Ответы карточки и `/reply` используют один журнал `owner_messages`.
  При принятии Telegram записывается `sent`; прочтение пользователем этим не подтверждается.
- Исходный ключ сообщения хранится между заявками: replay не может отправить
  старый ответ другому клиенту после смены выбранной карточки.
- `failed` — подтверждённый отказ, `unknown` — неподтверждённая доставка.
  Оставшийся после сбоя `sending` также требует проверки человеком.
- Архив хранит попытки в `archive_deliveries` внутри той же заявки.
  Известные ошибки повторяются с экспоненциальной задержкой, максимум пять
  автоматических попыток; владелец может повторить их из карточки.
  `sent`, `unknown` и незавершённые `sending` автоматически не повторяются.
- Ключи и приватные идентификаторы журнала архива не выдаются клиентскому API.
- Входящие и явные материалы сохраняются независимо от вторичного архива.
  Telegram file_id хранится для повторного открытия без скачивания на Render.

## Зависимости и ограничения

- Для сохранности production нужны существующие рабочие Upstash credentials.
  Их значения в ходе этой работы не читаются и не меняются.
- Публичный импорт использует Telegram embed/CDN, доступность которого зависит
  от Telegram. Видеоальбомы не поддерживаются этим импортным путём. Ошибка
  полного фотоальбома не превращается в частично опубликованный проект.
- Редактирование опубликованного источника не перезаписывает утверждённый кейс.
  Корзина и отклонённые работы сохраняются; черновики не выдаются публике.
- При отсутствии username ответы через бота доступны, если пользователь ранее
  взаимодействовал с ним и не заблокировал его. Прямая ссылка по ID зависит от Telegram.
- Фоновые повторы работают в существующем процессе и приостанавливаются вместе
  с Render Free. Не создаются keep-alive сервисы или платные worker-ресурсы.
- Исторические копирования, выполненные до появления журнала, не восстанавливаются
  в нём задним числом и не отправляются повторно автоматически.
- Мобильный browser smoke в рабочей среде заблокирован системным ограничением
  сокетов Chromium. JS-регрессии проходят; визуальный результат не объявляется проверенным.
- Render API требует подтверждения рабочего пространства; до этого его
  внутренний статус `live`/журналы нельзя считать повторно проверенными.
  HTTP и запущенный SHA можно проверять независимо через `/health`.

## Ручная приёмка владельцем

Используйте свой тестовый аккаунт, без сообщений реальным заказчикам.

1. Открыть Mini App: портфолио → проект/галерея → услуга → расчёт → бриф → отправка.
2. Проверить «Мои заявки», статус, дополнение и возврат; повтор отправки не создаёт дубль.
3. Из карточки нажать «Написать заказчику»; проверить адресата, переносы, `<`, `&`, emoji.
4. В теме этой заявки отправить `/reply текст`; проверить доставку и историю в карточке/Mini App.
5. Ответить текстом/файлом с одной заявкой, затем с несколькими: проверить выбор и подпись.
6. Повторно нажать старую кнопку выбора: нет повторного копирования и перепривязки.
7. Открыть входящий файл из «Материалов», проверить полную «Переписку» и возврат.
8. Проверить заблокированного получателя: нет ложного успеха; ответ остаётся в истории.
9. Опубликовать тестовый фотоальбом в канале: один черновик, порядок, подпись; отредактировать,
   выбрать категорию, опубликовать; ручные правки не затираются.
10. После restart/redeploy и сна Render Free повторить чтение заявок/истории/медиа;
    проверить SHA `/health`, отсутствие повторных отправок и ошибки в Render.

Техническая поставка не равна полной приёмке, пока внешний статус Render и
ручные проверки не подтверждены. Никакие production-данные не очищаются для теста.


## Пакет брендированного запуска

Существующий frontend экспортируется на CDN; backend/webhook/Redis остаются
прежними. Лёгкий SVG/CSS-лоудер закрывает ожидание `/health`, затем открывает
тот же Mini App. Включены строгий CORS, перенос черновика по postMessage с
проверкой origin/source, остановка запросов в фоне, reduced motion, тайм-аут и
ручной повтор. Тариф backend не меняется, новые платные ресурсы не нужны.
Критерии приёмки: статика открывается независимо от спящего backend;
HTML Render не принимается за API; Telegram-подпись, собственные заявки,
создание/дополнение, изображения и все launch-paths продолжают работать.
Старые inline-ссылки и отдельный Main Mini App URL в BotFather требуют
учёта при переключении; повтор холодного запуска внутри Telegram — MANUAL TEST PENDING.

## Визуальное оформление Mini App

Ручное добавление кейса, как и импорт из канала, сохраняет черновик.
В конце мастера доступны «Опубликовать», «Редактировать» и «Оставить в черновиках».
Повторное управление выполняется через существующие «Статусы и публикация».
Старые кейсы без статуса сохраняют прежнюю публичную видимость.

Существующие экраны получили единую сине-фиолетовую палитру, тёмные поверхности
и светлый вариант для Telegram light theme. Статические градиенты и тонкие
границы создают глубину без blur/WebGL/видеофона. Навигация сохраняет прежние
ID и настройки видимости, использует inline SVG и aria-current. CTA портфолио
ведёт в существующий бриф без сброса черновика. Логика расчёта, заявки,
подпись Telegram и серверные данные не меняются. Системные шрифты, lazy loading
галереи и отсутствие постоянных анимаций ограничивают затраты на загрузку.
